## New — MSP Payload Bounds Hardening (needs a decision, 2026-08-20)

Spun out of the now-resolved `audit-msp-set-handler-bounds-checking` (#19):
investigating a compile-time-enforced design to prevent that *class* of bug
surfaced a real, separate, previously-unreported defect. Full write-up:
`claude/developer/workspace/harden-msp-set-handlers-safe-reads/proposal.md`
(gitignored scratch space — move into project directories if this becomes
projects).

- **Project A (real defect, recommend HIGH/do first):** `mspProcessSensorCommand`
  explicitly discards the payload length (`UNUSED(dataSize)`) before handing
  a raw pointer to sensor receivers (GPS/compass/baro/airspeed/opflow/
  rangefinder) that cast it to fixed-size structs and read every field. A
  short-but-CRC-valid frame (e.g. from a buggy/mismatched MSP sensor
  peripheral) causes stale prior-frame bytes to be read as sensor data and
  fed to navigation. Not a memory-safety bug (reads stay inside the 192-byte
  `inBuf`) but a real correctness gap. Fix is ~1 line per handler.
  **Two decisions needed:** (1) whether/how to disclose on #11672 or
  privately — not yet posted, deliberately left to Ray as maintainer; (2)
  the existing #11672 audit comment (all 6 originally-flagged handlers are
  correctly bounded) remains true but now reads narrower than it should —
  may want a clarifying note.
- **Project B (compile-time bounds, Medium-Large):** convert 3 fixed-layout
  SET handlers to packed structs with `STATIC_ASSERT`-pinned `sizeof` guards
  so a future field addition becomes a build failure, not a silent
  wire-format break. Two of the three mutate the live control profile —
  needs field-by-field review, not just a build check.
- **Project C (optional, lowest priority):** sticky-overrun `sbuf_t` flag for
  the 2 genuinely variable-length handlers. Both are correct today; could
  reasonably be dropped.

Suggested sequencing: A, then B, then C if still worth it.
